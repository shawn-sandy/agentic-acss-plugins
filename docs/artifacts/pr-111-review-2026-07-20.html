Verdict

The right architectural call, executed with real rigour, shipped with one paperwork casualty. Choosing Browserslist's native baseline widely available query over a vendored baseline_check.py is correct and well argued: the repo's Python is stdlib-only, Baseline data lives in npm, and a vendored snapshot would rot silently. One config line reaches autoprefixer, Lightning CSS, esbuild and stylelint-browser-compat for free. That is the laziest solution that actually holds.

The review round-trip is the strongest part of this PR. Three genuine correctness defects in the instructions were caught and fixed in the second commit — the @supports ordering inversion in particular would have produced enhancements that are dead code with no error message. The fixes are not patches over symptoms; each rewrites the rule and states why the rule is that way.

What warrants the team's attention is not the design, it is the gap between what this PR claims and what anything can check. The 0.6.0 section of the style-agent changelog was destroyed by this diff and nobody noticed, because nothing looks. The Baseline gate has no Baseline data source. Eight verification runs are described in prose and none of them are re-runnable. All three are the same problem in different clothes.

The gate, in its own vocabulary

Baseline's three states map one-to-one onto three emission behaviours. This is the substance of the PR — everything else is plumbing that gets the classification to the right place.

Widely available≥ 30 months interop

Emit bare. No @supports, no fallback, no narration beyond the summary line. Flexbox and border-radius don't even reach the gate — it fires only for modern features.

Newly availablelanded < 30 months ago

Fallback first, then the @supports block. Name the fallback in the summary. Inline mode can't carry @supports, so this becomes a refusal there.

Limited availabilitynot interoperable

Withhold. Emit the fallback alone plus a one-line reason, so the user can override deliberately rather than discovering the omission later.

Two rules keep the ladder from being gamed. A declared browser target can tighten an outcome but never relax one — last 2 versions includes each browser's previous release, which may predate a Newly-available feature landing. And naming a feature is not a waiver: "using field-sizing" is intent, not consent. An explicit override in words moves an outcome by exactly one step, so Limited can reach @supports-with-fallback but never bare emit.

The bug the review caught

Worth reading closely, because it is the kind of defect that produces no error anywhere. The first commit told the skill to emit "inside @supports with a working fallback below it." Both rules share a selector and specificity, so the later one wins:

/* first commit — the enhancement is dead code */
@supports (grid-template-rows: subgrid) {
  .card { grid-template-rows: subgrid; }   ← applies…
}
.card { grid-template-rows: auto auto; }   ← …then loses, in exactly
                                              the browsers that support it

/* second commit — source order is load-bearing */
.card { grid-template-rows: auto auto; }   ← everyone gets this
@supports (grid-template-rows: subgrid) {
  .card { grid-template-rows: subgrid; }   ← supporting browsers upgrade
}

The instruction contradicted progressive-enhancement.md, which had the order right in the same diff — a two-document inconsistency that a read-through of either file alone would never surface. The fix states the ordering in both documents and explains that it is cascade mechanics, not style preference. That is the correct depth of fix.

F2

The Baseline gate has no Baseline data source

Medium · design

The gate classifies each feature as Widely / Newly / Limited, and its correctness rests entirely on that classification. But nothing in the skill supplies the data. It says "do not assert dates from memory" — good — and then asks for a status level, which is the same recall problem one abstraction up. The webstatus.dev pointer is conditional ("when status is genuinely uncertain"), and a model that is confidently wrong is by definition not uncertain.

This is the sharp edge of the build-vs-buy decision. Declining to vendor a rotting snapshot was right. But the alternative shipped here isn't the ecosystem tool — /setup gets Browserslist, /css gets model recall. The failure mode is quiet and asymmetric: a feature recalled as Widely when it is Newly emits bare and drops a fallback, and the summary line will confidently report "Widely available" while doing it.

Suggested fixTwo options, both cheap. (a) Make the webstatus.dev lookup mandatory rather than a fallback — one fetch per novel feature, cached for the session, with the gate refusing to classify without it. (b) Keep recall but require the summary to mark unverified classifications explicitly (Newly available (unverified)), so the uncertainty travels with the output instead of being smoothed away. (a) is more correct; (b) is a one-line edit and strictly better than today.

F3

Eight verification runs, zero re-runnable checks

Medium · test strategy

The PR describes eight skill runs against purpose-built fixtures, and is admirably specific about what each proved. That method is right — two instruction defects surfaced only because identical input produced divergent CSS across fixtures, which no read-through would have caught. The problem is that none of it survived the PR. The fixtures aren't committed, the runs aren't scripted, and tests/ contains no mention of Baseline or Browserslist.

So the evidence for the most subtle behaviour in either plugin is a table in a merged PR description. The next person to edit the Baseline gate has no way to know they broke the "target never relaxes" rule short of repeating the whole exercise by hand.

Suggested fixNot "test the prose" — that's a research project, and the same conclusion #109's review reached about the reference set. Commit the fixture projects (four tiny directories: no target, package.json key, .browserslistrc, plain browserslist) and add a structural gate that asserts Step 6.5 names all three lookup locations and that the gate's three outcomes are each present in SKILL.md. It won't prove the model behaves; it will catch a rule being deleted or reworded away, which is the realistic regression.

F4

Browserslist searches parent directories; Step 6.5 checks only the project root

Medium · correctness

The review fix correctly expanded the probe from two locations to three. But all three are anchored at <projectRoot>, and Browserslist walks up the directory tree from the working directory until it finds a config. In a monorepo with a shared browserslist at the repo root and packages beneath it, all three checks miss, /setup writes a package-local .browserslistrc, and that file now outranks the shared config for that package.

That is precisely the silent retargeting the skip exists to prevent, just moved one directory up. The original CodeRabbit finding said "current or parent directories"; the fix absorbed the file it named and dropped the traversal.

Suggested fixExtend the probe to walk parent directories to the repo root (stop at .git), and when a parent-level target is found, record it in kept[] with its path so the user can see which config claimed the project. Roughly one sentence added to Step 6.5.

F5

An editorial aside leaked into a literal output template

Process · authoring

The /setup summary block is a fenced template the skill reproduces verbatim for the user. The new line reads:

Created:
  - .acss-target.json
  - .browserslistrc     (omit when Step 6.5 skipped; it goes under Kept instead)

That parenthetical is an instruction to the model, sitting inside text the model is told to print. Every other conditional in the file lives in prose outside the fence. The Kept (already present): example directly below still lists only sass in devDependencies, so the skipped branch has no worked example at all — the one case the reviewer specifically asked to be made visible.

Suggested fixMove the condition to a sentence beneath the fence, and add the kept-branch line to the Kept example (- package.json browserslist (existing target, left alone)). Two-line edit; removes the chance of the aside being echoed to a user.

F6

Popover is now documented as below the bar the same repo writes

Process · worth watching

Not a defect — the honesty here is the good part, and the alternatives were worse. But note the shape of what shipped: /setup writes baseline widely available, and /kit-add popover generates a component that does not meet it. The resolution is three paragraphs of prose in two files explaining why that is fine.

It is fine, and the reasoning is sound — the native API is the accessible one, and JS alternatives reimplement focus handling and usually get it wrong. The thing to watch is that this is the first documented divergence between the target the tooling asserts and the code the tooling emits. If a second one appears, prose in the component doc stops being a scalable answer.

Suggested fixNothing now. If a second component crosses the same line, the answer is probably a machine-readable baseline: field in each component's front-matter plus a /kit-add warning, not more prose. Worth deciding before it's forced.

Open questions for the team

  1. Does the Baseline gate need a real data source before it's trustworthy?

    F2 is the load-bearing question in this PR. "Look it up when unsure" only works if uncertainty is detectable. Mandatory lookup costs a fetch; unverified-marking costs a line. Doing neither means the summary asserts a status with no backing.

  2. What is the minimum test that would have caught F1?

    A destroyed release section passed a green suite. A changelog shape check is small and catches a whole class — but it's the third PR in a row where the answer to "what would have caught this" is a check nobody has written yet. Worth deciding whether structural gates on markdown are in scope for tests/run.sh generally.

  3. Should skill-verification fixtures be committed?

    Eight manual runs is real work that evaporated on merge. tests/setup.sh already builds a sandbox fixture — extending it with browser-target variants is the obvious home, if the team wants agent-config changes to leave re-runnable evidence.

  4. Is prose the right long-term answer for components below the target?

    F6. One documented exception is fine. The question is what the second one triggers — a front-matter field and a /kit-add warning, or more paragraphs.
