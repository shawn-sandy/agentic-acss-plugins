A fourth style-agent skill that authors CSS from a plain-language description, where the existing three only transform styles that already exist. Eight bundled references carry the modern-CSS gotcha knowledge; a tinycss2 gate keeps their code fences parseable.

Verdict

Sound work that shipped too fast. The skill contract is unusually well specified for a prompt artifact — the clarification gate, the three-tier token resolution, and the "never invent a custom property" inversion are all reasoned rather than assumed, and the reference set targets real footguns rather than restating MDN. The new validator is correct and I re-ran it green.

Two things are worth the team's attention. First, there is a live contradiction inside SKILL.md between the inline-mode refusal list and the focus-visible step — which is also the crux of the one review finding the author declined, so declining it left the ambiguity in place rather than resolving it. Second, the automated gate validates the least valuable property of the deliverable: CSS fences tokenize, while the gotcha claims that are the actual product have no coverage at all.

Nothing here argues for a revert. F1 is a follow-up patch; the rest is process and test-strategy discussion.

Findings

F1

Inline mode and the focus-visible step contradict each other

High · correctness

The inline-mode branch refuses inline output when the description "implies" any of seven things — item 2 on that list is :focus-visible. The focus-visible step three sections later says an interactive element always gets a :focus-visible rule emitted, and that inline mode should warn about its absence instead.

So for the single most common inline request — a button — the file gives two incompatible instructions. If the auto-emit rule counts as "implying :focus-visible", inline mode must refuse and the warning path is dead code. If it doesn't, the refusal list's item 2 only ever fires when a user types the words "focus" — a much narrower rule than it reads as.

SKILL.md:72-80   Refuse inline mode … when the description implies:
                   2. :focus-visible

SKILL.md:90-91   emit a :focus-visible rule alongside the requested styling
                 … warn about its absence in the summary

This is also exactly the CodeRabbit finding that was declined. The decline rationale — that the plan's Step 5 specifies the warning path — is a reasonable process instinct, but it answers "which document wins" rather than "which behaviour is correct", and it leaves the two clauses disagreeing regardless of which one was intended.

Suggested fixPick one and edit both places in the same commit. My recommendation is refusal: an inline style attribute on a button that ships with no focus indicator is a WCAG 2.4.7 failure written into the user's markup, and a warning printed to chat does not travel with the code. A chat warning is the right tool for something recoverable; this isn't. Amend the plan alongside the skill so the two stay in sync.

F2

The test gates syntax; the deliverable is correctness

Medium · test strategy

The PR description is explicit that "the real deliverable is the gotcha knowledge, not the words-to-properties transform." The validator's own docstring is equally explicit that it is "a tokenizer-level syntax gate, not a correctness gate" — it will happily accept an invalid container-type keyword or a :has() containing a pseudo-element.

Both statements are honest. Together they mean the automated coverage sits entirely on the property nobody was worried about. A reference could be silently rewritten to claim layered styles beat unlayered ones and every test would stay green.

Suggested fixNot "test the prose" — that's a research project. Two cheap gates buy most of the value: (a) assert each reference file still contains its one load-bearing claim, as a literal substring pinned in the test; (b) assert every ${CLAUDE_PLUGIN_ROOT}/… path in the SKILL.md reference table resolves on disk. The second is roughly five lines and catches the most likely real regression — a renamed reference silently breaking the skill's own lookup table. There is currently no such check anywhere in tests/.

F3

References are banned from showing SCSS, but the skill emits SCSS

Medium · consistency

The validator hard-fails any ```scss fence: "the css references are plain-CSS-only by decision." Meanwhile the skill infers SCSS versus plain CSS from the project's dominant stylesheet flavour and emits SCSS accordingly, and modern-selectors.md is listed as covering "native nesting vs SCSS &."

The consequence is that the reference set can never demonstrate the SCSS half of the skill's own output contract — the nesting comparison has to be described rather than shown on one side. The decision may still be right (one flavour keeps the gate simple), but it should be a stated trade-off rather than an unexamined constraint, especially as the SCSS path grows.

Suggested fixEither allow scss fences and skip them from tinycss2 parsing while still requiring them to be fenced and closed, or record the plain-CSS-only rule in the reference-authoring rule doc so the next author hits the reason rather than the error.

F4

Fence-opener regex misses fences with attributes

Medium · test soundness

The opener pattern is ^(\s*)(`{3,}|~{3,})\s*([A-Za-z0-9_+-]*)\s*$. It matches ```css but not ```css title="example" or any other info-string with a space. Such a fence isn't skipped cleanly — it is never recognised as an opener, so the scanner keeps walking into its body and can pick up a phantom opener from the content inside it.

No current reference uses an attributed fence, so this is latent rather than live. It is the same class of bug as the unterminated-fence hole CodeRabbit caught, which suggests the fence parser deserves one more pass rather than one more patch.

Suggested fixCapture the first whitespace-delimited token as the language and ignore the remainder of the info string, rather than requiring the whole line to be language-only.

P1

The final commit was merged with no completed review

Process

Timeline: opened 12:46, review-fix commit ee3791b at 12:56, merged 13:04 — eight minutes after the fixes landed and eighteen after opening. Copilot returned a quota error on both attempts. CodeRabbit hit its rate limit and posted "next review available in 8 minutes," listing five files it had not yet reviewed — including SKILL.md, tests/run.sh, and validate_reference_css.py, i.e. every file the fix commit touched. No human review is recorded.

Worth naming plainly because the standing repo guidance is the opposite concern — don't loop endlessly on re-firing bots. That guidance is about re-review of already-approved work. Here the first pass on the final commit never completed, which is a different situation and the one case where waiting was cheap.

Suggested fixNo action on this PR. Worth a shared rule of thumb: a merge is fine once one reviewer has completed a pass on the commit being merged — bot or human. "Rate limited" is not "approved."

P3

A declined nitpick contradicted a repo rule and went unrecorded

Process

CodeRabbit's nitpick asked to move summary and emission presentation out of SKILL.md and into commands/css.md. .claude/rules/command-authoring.md says the opposite: "Body must delegate to the master SKILL.md — never re-implement logic inline." Ignoring it was correct. But the author's reply comment tabulates five applied findings and one declined, and this one appears in neither.

Low stakes on its own; it matters because the next reviewer — or the next bot run — will raise the same suggestion with no record of why it was rejected.

Suggested fixList silently-ignored findings in the reply with a one-line reason. Here: "contradicts .claude/rules/command-authoring.md."

Worth keeping

  • The token-creation inversion is well argued. /css never invents a custom property, deliberately opposite to inline-style-to-class, and SKILL.md states the reason: there the value is already committed to the user's markup, here a throwaway request would write into someone's design system. That is a real distinction, reasoned rather than asserted.
  • "Read the whole scale before mapping a relative word." Treating "small" as a position in a scale rather than a value, with a clarification trigger for adjacent-step ties, is the correct model — and consistent with prior feedback on this repo about preserving scale distinctness.
  • The clarification gate has a skip path. A fully-specified description is emitted with no questions. Gates that always fire are how skills become annoying.
  • References state the failure, not the feature. cascade-layers.md leads with "unlayered styles win" and names the symptom ("my @layer refactor changed nothing"). That is the shape that actually prevents a wrong answer.
  • The known-bad fixture carries both rejection modes. After the hardening commit, a regression in either branch fails by name instead of being masked by the other. That is better than most validators in this repo.
  • The .sass exclusion is a genuinely good catch from the Codex pass — brace-and-semicolon output is invalid in indented Sass, and it now refuses rather than corrupting a file.

For the team to settle

1 · Warning or refusal when a mode can't carry a required a11y state? F1 forces the question. Refusal is safer but makes inline mode nearly useless for interactive elements — which may be the honest answer. Whichever way it goes, the plan and the skill need editing together.

2 · What does a prompt-artifact test suite owe the reader? Syntax gates are cheap and catch little. Pinning load-bearing claims as literal substrings is slightly brittle but tests the thing being sold. Where should this repo sit?

3 · What's the merge bar when every reviewer is a rate-limited bot? P1 isn't unique to this PR and will recur.
