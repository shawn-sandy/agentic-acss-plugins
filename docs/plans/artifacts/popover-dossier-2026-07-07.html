Context

What already exists — and the gap

This was never a "build a popover" task. The repo already ships one.

The acss-kit component-popover skill generates a React popover built on the native HTML Popover API — popover + popovertarget + showPopover()/hidePopover(), auto/manual modes, light-dismiss, and top-layer rendering, with zero dependencies (no floating-ui, no radix). So the real work is closing the gap between "a centered card" and "a menu or tooltip that sits at its trigger."

Gap → fix, in priority order

One hard constraint shapes everything: the generator has two source files — a neutral popover.component.md and a byte-identical reference.md fallback. A golden test diffs their extracted SCSS, so every change lands in both or CI goes red.

Approach

Progressive enhancement, inverted

CSS Anchor Positioning ships in Chrome/Edge 125+ and Safari 26+ — but not Firefox. So the base rule is the fallback that works everywhere, and the @supports (anchor-name) block layers the anchored version on top. Browsers that don't understand it never enter the block. No polyfill required, no JS branch.

The subtle part: a shared anchor-name would bind every popover to the nearest matching trigger — breaking the headline multi-instance case (a nav with several dropdowns). So the anchor-name/position-anchor pair rides in as an inline style keyed off the component's already-generated unique id. In a non-supporting browser it's just an unknown property — ignored, harmless.

Review

Seven reviewers, and what they caught

The draft plan went through an Agent Team — architecture, completeness, testability, risk, conventions, UX, accessibility. Several read the actual repo, so the findings are concrete, not generic. All of these were folded back into the plan before it was committed.

critical
Golden SCSS fixture never regenerated — completeness, risk, architecture
tests/run.sh §2a diffs extracted SCSS against tests/fixtures/golden/component-popover/popover.scss. Any SCSS edit fails on golden DRIFT until that fixture is refreshed — the draft never listed it.
Applied New Step 9 regenerates the fixture; Files list + Context corrected.
critical
role="menu" on nav links is an ARIA anti-pattern — accessibility, ux
A set of links dressed as role="menu" promises arrow-key roving-tabindex the plan doesn't build — assistive tech announces a contract the code breaks (WCAG 4.1.2).
Applied Switched to the WAI-ARIA Disclosure Navigation pattern (trigger aria-expanded + plain link list).
critical
E2E test wasn't a committed file; jsdom can't evaluate anchoring — testability
The "E2E" was an ad-hoc MCP session, and jsdom has no layout engine — anchor-name/position-try are inert there. The anchored half of the objective had no repeatable guard.
Applied A committed Playwright spec (Chromium + Firefox); jsdom scoped to markup/ARIA only.
high
Shared vs. per-instance anchor-name — architecture
A class-level anchor name resolves to the nearest matching trigger, so multiple popovers on one page bind wrong — exactly the dropdown-nav use case.
Applied Per-instance names via inline style keyed off the generated id (Step 1 + AC8).
high
Tooltip failed WCAG 1.4.13 — accessibility, ux
A naive mouseenter/leave handler flickers, closes before you can read it, and excludes touch and keyboard. 1.4.13 requires hoverable + dismissible + persistent.
Applied Intent delay, listeners on the popover too, Escape dismiss, tap path (Step 5 + AC9).
high
Breaking visual change with no version bump — risk
Anchor CSS shifts where existing installs render on re-sync. The repo's pre-submit checklist requires a version bump + changelog for user-facing changes.
Applied New Step 10 bumps plugin.json + CHANGELOG (AC11).
high
Parity mechanism misattributed; stale docs; filename mismatch — completeness, conventions
The plan named the wrong parity guard, left the "user must add role" prose that the feature makes false, and never reconciled popover.module.scss vs popover.scss.
Applied New Step 8 (a11y prose + token tables); filename reconcile in Step 1; AC10.
Decisions

Calls made this session

chosen @supports fallback default

CSS progressive enhancement, zero runtime. Firefox gets approximate placement until it ships anchoring natively.

Alt considered: JS positioning (getBoundingClientRect) — rejected, it reintroduces the library the native API replaced.

chosen Disclosure over role="menu"

A nav dropdown of links uses aria-expanded disclosure, not menu semantics. role="menu" waits for real keyboard support in a component-nav follow-up.

A role must not out-run the interaction it implies.

chosen Polyfill = opt-in, not baked in

OddBird's @oddbird/css-anchor-positioning is documented as a consumer-side feature-detected import — never a dependency of the generated component. Keeps dependencies: [].

Added to the plan's Next Steps for teams that need pixel-accurate Firefox anchoring.

chosen Enhance, don't rebuild

Everything lands in the two existing source docs, kept byte-identical. No new component, no parallel implementation.

The dual-source golden guard is the safety net for every edit.
